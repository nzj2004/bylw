## 1. 项目概述

本项目是一个前后端分离的毕业生招聘信息发布与管理系统，面向管理员、运营人员、企业用户、求职者四类角色，覆盖账号认证、企业审核、职位发布与审核、职位浏览搜索、简历维护、投递记录、企业端简历处理、面试轮次、Offer响应、入职确认、收藏、文件上传、操作日志与统计看板等功能。

系统整体技术栈如下：

| 层级 | 技术 |
|---|---|
| 前端 | Vue 3、Vite、Vue Router、Pinia、Element Plus、Axios、ECharts、xlsx |
| 后端 | Spring Boot 3.1.6、Spring Security、JWT、MyBatis-Plus、MySQL、Lombok、AOP |
| 数据库 | MySQL 8.0，核心表包含用户、企业、职位、简历、投递、状态历史、面试、Offer、站内通知、收藏、操作日志 |
| 文件上传 | 图片与 PDF 上传，区分 `images/` 和 `pdfs/` 存储目录 |

## 3. 已实现核心功能

### 3.1 通用与认证

- 用户注册、登录、JWT 鉴权、Spring Security 接口权限控制。
- 四类角色：管理员、运营、企业、求职者。
- 前端路由根据角色做访问控制，后端通过 `@PreAuthorize` 做接口鉴权。
- 操作日志通过 AOP 自动记录，支持后台查看与筛选。

### 3.2 管理员端

- 用户管理：列表、筛选、新增、禁用/启用、删除、重置密码。
- 职位管理：查看、编辑、删除、上下线状态控制。
- 批量发布：支持 Excel 导入职位并批量发布。
- 数据看板：系统关键数据统计与可视化。
- 日志管理：查询系统操作记录。

### 3.3 运营端

- 企业审核：查看企业资料，按状态筛选，审核通过或拒绝。
- 职位审核：审核企业发布的职位，支持单个审核、批量审核、分页与筛选。

### 3.4 企业端

- 企业资料维护：编辑企业信息、上传 Logo、提交审核、查看审核状态。
- 职位管理：发布、编辑、删除职位，职位默认进入待审核状态。
- 应聘管理：查看投递记录、筛选职位/类别/状态、查看求职者简历、标记“感兴趣”或“不合适”。
- 面试流程：为候选人创建面试轮次，维护面试时间、地点/链接、联系人、备注与面试结果。
- Offer管理：向候选人发送或更新Offer，维护薪资、福利、入职日期、工作地点与有效期。
- 入职确认：Offer被求职者接受后，企业可确认候选人已入职。

### 3.5 求职者端

- 职位浏览：首页推荐、职位列表、职位详情。
- 职位搜索：关键字、城市、经验、学历、薪资、类别等筛选。
- 简历管理：维护个人信息、教育经历、工作/项目经历、技能、自我评价。
- 文件能力：支持头像/照片类图片上传，支持 PDF 简历附件上传。
- 投递管理：投递职位、查看投递记录、面试进度与企业处理状态。
- 面试处理：查看企业安排的面试，支持确认面试和申请改期。
- Offer处理：查看收到的Offer，并支持接受或拒绝。
- 站内通知：查看通知列表、未读数，支持单条已读和全部已读。
- 职位收藏：收藏、取消收藏、收藏列表、从收藏进入投递。

## 5. 当前招聘流程完成度

### 5.1 已覆盖流程

当前系统已经覆盖从企业入驻到候选人入职确认的主流程闭环：

1. 企业注册账号。
2. 企业填写资料并提交审核。
3. 运营审核企业，通过后企业具备招聘资格。
4. 企业发布职位。
5. 运营或管理员审核职位。
6. 职位发布到求职者端。
7. 求职者浏览、搜索、收藏职位。
8. 求职者完善简历并投递职位。
9. 企业查看投递列表与简历详情。
10. 企业查看简历时自动把待查看投递流转为“已查看”。
11. 企业初筛候选人，标记“感兴趣”或“不合适”。
12. 企业为候选人安排面试，并维护面试结果。
13. 面试通过后企业发送Offer。
14. 求职者查看Offer并接受或拒绝。
15. Offer被接受后，企业确认候选人已入职。
16. 求职者在“我的投递记录”和Offer页面查看处理进度。

### 5.2 招聘流程还差多少环节

按一个完整招聘闭环计算，当前主流程已经基本打通，剩余问题主要集中在历史数据治理和测试覆盖：

| 待完善点 | 当前情况 | 建议补齐内容 |
|---|---|---|
| 1. 历史数据治理 | 本轮已统一新代码中企业/职位/投递的公司ID口径，并补充了核查SQL，但旧数据仍需执行审计 | 运行 `audit_company_id_consistency.sql` 并按结果决定是否迁移 |
| 2. 自动化测试 | 目前主要依赖编译构建和手工流程验证 | 补充后端接口测试与前端关键流程测试 |

因此，当前项目已从“职位发布、审核、投递、初筛”推进到“面试、Offer、入职确认”的招聘闭环阶段；后续重点应放在体验完善、状态语义精细化和数据一致性治理。

## 6. 当前观察到的主要问题与优化建议

### 6.1 招聘流程

- 面试通过与Offer待确认已经拆分：面试通过后进入“面试通过”，企业真正发送Offer后才进入“Offer待确认”。
- Offer过期已经由定时任务和Offer列表查询触发处理，超期待确认Offer会更新为“Offer已过期”。
- 投递状态变更历史已经落表，企业端和求职者端都可以查看状态时间线。
- 求职者端已支持面试确认和申请改期，企业端可查看确认状态并同意改期。
- 站内通知已支持通知列表、未读数、标记已读；面试、Offer、投递状态变化会产生通知。

### 6.2 数据与权限

- 当前代码已统一新写入逻辑：`job_info.company_id` 与 `application.company_id` 均按 `company_info.id` 使用，SQL也改为关联 `company_info.id`。
- 如果数据库中已有旧数据，需要检查是否存在按 `sys_user.id` 写入的 `company_id`，否则旧职位和旧投递可能无法正确关联企业信息。
- 企业发布职位已校验企业审核通过状态；如果需要管理员代发职位，仍需确保传入的 `companyId` 是企业资料ID。
- 求职者端 Offer 接口已修正为 `/api/user/offers` 和 `/api/user/offer/{offerId}/response`，避免原先路径多一层 `/user` 导致的无权限/请求失败提示。
- 前端已对求职者端投递、Offer、通知等页面的 403/无权限类错误做静默处理，避免连续弹出“没有权限执行该操作”；401 登录失效仍会提示重新登录。

### 6.3 测试数据
