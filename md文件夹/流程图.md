## 系统功能需求分析

### 功能模块总览

系统采用前后端分离架构，基于RBAC（基于角色的访问控制）模型，实现四角色权限管理。整体功能划分为 **13个核心模块**，涵盖用户认证、企业管理、职位管理、简历投递、面试/Offer、站内通知、收藏管理、数据统计等功能。

|---------|:---:|:---:|:---:|:---:|:---:|
| **用户认证** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **用户管理** | ✅ 全部权限 | ❌ | ❌ | ❌ | ❌ |
| **企业信息** | ✅ 查看 | ✅ 审核 | ✅ 管理 | ❌ | ❌ |
| **职位管理** | ✅ 全部权限 | ✅ 审核 | ✅ 发布/管理 | ❌ | ✅ 浏览 |
| **简历管理** | ✅ 查看 | ❌ | ❌ | ✅ 管理 | ❌ |
| **投递管理** | ✅ 查看 | ❌ | ✅ 处理投递 | ✅ 投递 | ❌ |
| **站内通知** | ✅ 查看 | ✅ 查看 | ✅ 查看/接收 | ✅ 查看/接收 | ❌ |
| **收藏管理** | ❌ | ❌ | ❌ | ✅ 收藏 | ❌ |
| **运营审核** | ✅ 代替审核 | ✅ 审核 | ❌ | ❌ | ❌ |
| **统计分析** | ✅ 全局统计 | ❌ | ✅ 企业统计 | ❌ | ❌ |
| **日志管理** | ✅ 查看/清理 | ❌ | ❌ | ❌ | ❌ |
| **文件上传** | ✅ | ✅ | ✅ | ✅ | ❌ |
| **批量发布** | ✅ | ❌ | ❌ | ❌ | ❌ |

- ✅ 表示该角色拥有此功能的完整权限

#### 数据流转关系

**核心业务流程数据流转：**

1. **用户注册登录**
   ```
   用户输入 → sys_user表验证 → 生成JWT → 返回Token
   ```

2. **企业审核流程**
   ```
   首次提交 → company_info表(状态=0) → 运营审核 → company_info表(状态=1/2)
   已通过企业修改 → pending_*字段暂存 → 提交审核并下架岗位 → 运营审核通过后覆盖正式资料
   ```

3. **职位发布流程**
   ```
   企业发布 → job_info表(状态=0) → 运营审核 → job_info表(状态=1) → 求职者可见
   ```

4. **职位投递流程**
   ```
   求职者投递 → application表(状态=0) → 企业查看简历(状态=1) → 初筛(状态=2/3)
   → 安排面试 → 求职者确认/申请改期 → 记录结果(状态=4/5/10)
   → 发送/响应Offer(状态=6/7/8/11) → 确认入职(状态=9)
   → application_status_history表记录每次状态变更
   → user_notification表记录站内通知
   ```

5. **测试数据口径**
   ```
   insert_test_data.sql → 重置型演示数据脚本，会清理并重建演示业务数据
   repair_seed_chinese_data.sql → 非破坏性修复脚本，修复中文文案、薪资K单位、状态历史、通知样例
   expand_dashboard_demo_data.sql → 扩展到580家企业、1200个职位、8600个用户、3200条投递
   ```

## 2. 企业审核流程

### 2.1 企业信息提交与审核流程

```mermaid
sequenceDiagram
    participant E as 企业用户
    participant F as 前端
    participant C as UserController
    participant DB as 数据库
    participant O as 运营人员
    participant OC as OperatorController

    E->>F: 填写企业信息
    F->>C: POST /api/user/company/info
    C->>DB: 查询是否已有企业信息
    DB-->>C: 返回查询结果
    alt 首次创建
        C->>C: 设置状态为待审核(0)
        C->>DB: 插入正式企业资料
        DB-->>C: 插入成功
        C-->>F: 返回保存成功
        F-->>E: 显示等待审核
    else 已有企业资料
        C->>DB: 保存到pending_*待审核字段
        DB-->>C: 保存成功
        C-->>F: 返回保存成功
        F-->>E: 标识有待提交修改
    end

    E->>F: 点击提交审核
    F->>C: POST /api/user/company/submit-audit
    C->>DB: 更新企业状态为待审核(0)
    C->>DB: 将该企业岗位更新为已下线(3)
    DB-->>C: 更新成功
    C-->>F: 返回提交成功
    F-->>E: 显示信息正在审核

    Note over O,DB: 运营审核阶段
    O->>F: 查看待审核企业列表
    F->>OC: GET /api/operator/companies
    OC->>DB: 查询待审核企业与pending_*资料
    DB-->>OC: 返回列表
    OC-->>F: 返回数据
    F-->>O: 显示审核列表

    O->>F: 选择通过/拒绝
    alt 审核通过
        F->>OC: PUT /api/operator/company/{id}/audit?status=1
        OC->>DB: pending_*覆盖正式资料并清空pending_*
        OC->>DB: 更新状态为已通过(1)
        DB-->>OC: 更新成功
        OC-->>F: 返回成功
        F-->>O: 显示通过成功
    else 审核拒绝
        F->>OC: PUT /api/operator/company/{id}/audit?status=2
        OC->>DB: 更新状态为已拒绝(2)并记录原因
        OC->>DB: 确保该企业岗位已下线(3)
        DB-->>OC: 更新成功
        OC-->>F: 返回成功
        F-->>O: 显示拒绝成功
    end
```

**流程说明：**
1. 企业用户首次填写企业信息时，系统保存正式企业资料并设置为“待审核”。
2. 已通过企业再次修改资料时，修改内容先写入 `pending_*` 待审核字段，正式资料暂不覆盖。
3. 企业点击“提交审核”后，企业状态变为“待审核”，该企业下所有岗位自动下架。
4. 运营人员查看待审核企业列表，若存在资料变更，页面会标识“资料变更”。
5. 审核通过：`pending_*` 覆盖正式资料并清空，企业恢复已通过状态。
6. 审核拒绝：记录拒绝原因，企业资料不覆盖，岗位保持下架，企业需要修改后重新提交。

### 2.2 企业审核状态流转

```mermaid
stateDiagram-v2
    [*] --> 待审核: 提交企业信息
    待审核 --> 已通过: 运营审核通过
    待审核 --> 已拒绝: 运营审核拒绝
    已通过 --> 待提交修改: 保存资料修改到pending_*
    待提交修改 --> 待审核: 提交审核/岗位下架
    已拒绝 --> 待提交修改: 保存资料修改到pending_*
    待提交修改 --> 待审核: 重新提交审核/岗位下架
    已拒绝 --> [*]: 放弃申请
    已通过 --> [*]: 审核完成
```

**状态说明：**
- **待审核 (0)**：企业刚提交信息或修改后重新提交
- **已通过 (1)**：运营审核通过，企业可以发布职位
- **已拒绝 (2)**：运营审核拒绝，需要填写拒绝原因
- **待提交修改**：页面状态，表示企业已保存待审核修改但尚未提交审核；数据存储在 `pending_*` 字段。

## 4. 职位投递流程

### 4.1 求职者投递职位流程

```mermaid
sequenceDiagram
    participant U as 求职者
    participant F as 前端
    participant C as UserController
    participant S as ApplicationService
    participant DB as 数据库
    participant E as 企业用户

    U->>F: 浏览职位详情
    F->>C: GET /api/job/{id}
    C->>DB: 查询职位信息
    DB-->>C: 返回职位数据
    C->>C: 增加浏览量
    C-->>F: 返回职位详情
    F-->>U: 显示职位信息

    U->>F: 点击"投递简历"
    F->>F: 检查登录状态
    alt 未登录
        F-->>U: 弹出登录框
    else 已登录
        F->>F: 检查是否已有简历
        alt 没有简历
            F-->>U: 提示：请先完善简历
        else 有简历
            F->>C: POST /api/user/apply/{jobId}
            C->>S: applyJob(jobId)
            S->>DB: 检查是否已投递
            DB-->>S: 返回检查结果
            alt 已投递
                S-->>C: 返回错误：已投递过该职位

            else 未投递
                S->>DB: 获取默认简历
                DB-->>S: 返回简历信息
                S->>DB: 创建投递记录
                Note over S,DB: status=待查看(0)
                DB-->>S: 插入成功
                S->>DB: 更新职位投递数
                DB-->>S: 更新成功
                S-->>C: 返回成功
                C-->>F: 返回响应
                F-->>U: 提示：投递成功
            end
        end
    end

    Note over E,DB: 企业处理投递
    E->>F: 查看应聘管理
    F->>C: GET /api/user/company/applications
    C->>DB: 查询本企业投递记录
    DB-->>C: 返回列表
    C-->>F: 返回数据
    F-->>E: 显示投递列表

    E->>F: 查看简历详情
    F->>C: GET /api/user/resume/{resumeId}?applicationId={applicationId}
    C->>DB: 校验投递归属并查询简历
    alt 当前为待查看
        C->>DB: 自动更新为已查看
        Note over C,DB: status=已查看(1)<br/>记录viewed_at/viewed_by
    end
    DB-->>C: 返回简历详情
    C-->>F: 返回数据
    F-->>E: 显示简历

    F->>C: PUT /api/user/company/application/{applicationId}/status
    C->>DB: 校验状态与企业归属
    Note over C,DB: 仅支持已查看/感兴趣/不合适
    DB-->>C: 更新成功
    C-->>F: 返回成功
    F-->>E: 显示更新成功

    alt 企业继续推进面试
        E->>F: 安排面试
        F->>C: POST /api/user/company/application/{applicationId}/interviews
        C->>DB: 写入interview_rounds并更新投递状态
        Note over C,DB: status=面试中(4)

        E->>F: 录入面试结果
        F->>C: PUT /api/user/company/interview-round/{roundId}/result
        C->>DB: 更新面试轮次结果
        alt 面试未通过
            C->>DB: application.status=面试未通过(5)
        else 面试通过或继续下一轮
            C->>DB: 保持面试中或进入面试通过
        end
    end

    alt 企业发送Offer
        E->>F: 填写并发送Offer
        F->>C: POST /api/user/company/application/{applicationId}/offer
        C->>DB: 写入offers并更新投递状态
        Note over C,DB: application.status=Offer待确认(6)

        U->>F: 查看Offer列表
        F->>C: GET /api/user/offers
        C->>DB: 查询Offer
        DB-->>C: 返回Offer列表
        C-->>F: 返回数据
        F-->>U: 显示Offer

        U->>F: 接受或拒绝Offer
        F->>C: PUT /api/user/offer/{offerId}/response
        C->>DB: 校验Offer有效期并更新结果
        alt 接受Offer
            C->>DB: application.status=Offer已接受(7)
            E->>F: 确认已入职
            F->>C: PUT /api/user/company/application/{applicationId}/onboard
            C->>DB: application.status=已入职(9)
        else 拒绝Offer
            C->>DB: application.status=Offer已拒绝(8)
        end
    end
```

**流程说明：**
1. 求职者浏览职位详情，系统自动增加浏览量
2. 求职者点击投递简历
3. 系统检查登录状态和简历完整性
4. 检查是否已投递该职位（防止重复投递）
5. 创建投递记录，状态为"待查看"
6. 更新职位的投递数量
7. 企业查看投递列表
8. 企业查看简历时，待查看投递自动流转为"已查看"
9. 企业可做初筛处理：已查看、感兴趣或不合适
10. 对感兴趣候选人安排面试，并记录每轮面试结果
11. 面试通过后企业发送Offer，求职者接受或拒绝
12. Offer被接受后，企业确认入职，投递进入最终闭环

**权限检查规则：**

### 12.2 后端接口权限验证

```mermaid
sequenceDiagram
    participant C as 客户端
    participant F as JwtAuthenticationFilter
    participant S as Spring Security
    participant A as @PreAuthorize
    participant M as Controller方法

    C->>F: HTTP请求（携带Token）
    F->>F: 提取Token
    alt 无Token
        F-->>C: 401 未认证
    else 有Token
        F->>F: 验证Token有效性
        alt Token无效
            F-->>C: 401 Token过期或无效
        else Token有效
            F->>F: 解析用户信息
            F->>S: 设置SecurityContext
            S->>A: 检查@PreAuthorize注解
            alt 无权限注解
                A->>M: 放行执行
            else 有权限注解
                A->>A: 验证用户角色
                alt 角色匹配
                    A->>M: 放行执行
                else 角色不匹配
                    A-->>C: 403 禁止访问
                end
            end
        end
    end
```

**权限注解示例：**
- `@PreAuthorize("hasRole('ADMIN')")` - 仅管理员
- `@PreAuthorize("hasRole('COMPANY')")` - 仅企业
- `@PreAuthorize("hasAnyRole('OPERATOR', 'ADMIN')")` - 运营或管理员
- `@PreAuthorize("isAuthenticated()")` - 已登录用户
